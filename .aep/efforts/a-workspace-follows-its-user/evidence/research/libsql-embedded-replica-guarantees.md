# What a libSQL embedded replica and Turso actually guarantee

Verified against: Turso Cloud documentation and `turso.tech/pricing` as published 2026-08-13; `@libsql/client` 0.17.4 (which pins `libsql ^0.5.28`); `libsql` Rust crate and Hrana 3 specification at `tursodatabase/libsql@main`; `@tursodatabase/database` / `@tursodatabase/sync` at `tursodatabase/turso@main`, workspace version `0.8.0-pre.4`. Date: 2026-08-13.

`falsifies: []` — nothing here contradicts ADR 0027, ADR 0010 or [[contexts/persistence]]. Those are statements about the local SQLite engine reached through Tauri, and every one of them remains true of that transport. What this finding does is price a *third* transport; it retires no recorded claim.

## 1 — Does an embedded replica accept writes while disconnected?

**Not by default, and the default is the load-bearing one.** "**Writes are sent to the remote primary database** configured at `syncUrl` by default. They are NOT written to the local file first." — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "How it works", step 4. The same step adds "Any write transactions with reads are also sent to the remote primary database." A `@libsql/client` embedded replica in its default configuration is therefore **read-only when disconnected**.

**There is a documented offline-write mode, and it is now legacy.** "You can write locally if you set the `offline` config option to `true`." — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "How it works", step 4; the option is declared as `offline?: boolean` / "Enable offline writes" in [`libsql-core/src/api.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-core/src/api.ts), `Config`. Turso now steers away from it: "For workloads that need **offline writes**, **bidirectional sync**, or **multi-writer convergence**, we recommend [`@tursodatabase/sync`](#tursodatabasesync) — both reads and writes are local, and you sync explicitly with `push()` / `pull()`." — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), "@libsql/client → Embedded Replicas" Info callout. And: "This is the modern equivalent of the `offline: true` flag from [`@libsql/client` Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction)." — [Turso Sync Usage](https://docs.turso.tech/sync/usage), "Offline-first writes", closing paragraph.

**What `offline: true` does mechanically**, read in the version `@libsql/client` 0.17.4 actually pins: `if offline { libsql::Builder::new_synced_database(...) } else { libsql::Builder::new_remote_replica(...) }` — [`libsql-js@v0.5.28 src/database.rs`](https://github.com/tursodatabase/libsql-js/blob/v0.5.28/src/database.rs), lines 112–127. The two builders are documented in the Rust crate as: "`new_remote_replica`/`RemoteReplica` creates an embedded replica database that will be able to sync from the remote url and **delegate writes to the remote primary**" and "`new_synced_database`/`SyncedDatabase` creates a database that **can be written offline and synced to a remote server**" — [`libsql/src/database/builder.rs`](https://github.com/tursodatabase/libsql/blob/main/libsql/src/database/builder.rs), `Builder` doc comment, lines 14–22.

**A trap in that same code path: `syncInterval` is silently dropped when `offline` is set.** The offline branch of `libsql-js@v0.5.28 src/database.rs` (lines 112–123) applies `read_your_writes` and encryption but never calls `builder.sync_interval(...)`; only the non-offline branch does (lines 125–141). Periodic sync therefore does not run in offline mode in that version, and nothing errors. This is a code reading, not a documented statement — Turso's docs show `syncInterval` and `offline` set together in the same example ([Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "Periodic sync" snippet).

**Turso Sync is the supported offline-first path.** "If your app needs to accept writes without internet connectivity, write locally and call `push()` when the connection is available. All changes are safely stored in the local database file until they can be synced." — [Turso Sync Usage](https://docs.turso.tech/sync/usage), "Offline-first writes". Its first-connect behaviour has a catch: "On the first run, the local database is automatically bootstrapped from the remote — so the remote must be reachable during the initial connect. If you set `bootstrap_if_empty` to `false`, the local database will start empty instead." — same page, Step 2 Note. So a genuinely offline *first launch* requires `bootstrapIfEmpty: false` and an empty local database.

**What `sync()` does and when it must be called.** For embedded replicas it is one-directional pull-plus-reflect: "You should call `.sync()` in the background whenever your application wants to sync the remote and local embedded replica. For example, you can call it every 5 minutes or every time the application starts." — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "Usage" Note; `syncInterval` (seconds) automates it, same page, "Periodic sync". For Turso Sync the two directions are separate calls — `db.push()` sends local writes, `db.pull()` fetches remote changes and "returns a boolean indicating whether anything changed" — [Turso Sync Usage](https://docs.turso.tech/sync/usage), Steps 3 and 4; the JS package README adds `db.sync()` as "pull & push changes" — [`bindings/javascript/sync/README.md`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/README.md), "Getting Started".

**What a read sees between syncs.** "Reads are always served from the local replica configured at `url`." — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "How it works", step 3. Staleness is therefore bounded only by sync cadence: "Other replicas will see the new data when they call `sync()`, or at the next sync period, if Periodic Sync is used." — same page, "Read your writes". Read-your-own-writes is guaranteed *for the writing replica only*: "after a write returns successfully, the replica that initiated the write will always be able to see the new data right away, even if it never calls `sync()`" — same section; it is a toggle, defaulting on ("Set whether you want writes to be visible locally before the write query returns… This defaults to `true`." — [`libsql/src/database/builder.rs`](https://github.com/tursodatabase/libsql/blob/main/libsql/src/database/builder.rs), `read_your_writes`).

**Conflict on reconnect — two different answers, and one of them is undocumented.**

- Turso Sync: "Turso sync uses a **last push wins** strategy. When two clients modify the same data and push, the last push determines the final state on the remote." and, on pull with unpushed local changes, "1. Your local database is rolled back to the last synced state 2. Remote changes are applied 3. Your unpushed local changes are **replayed** on top… This rollback-and-replay happens atomically — if anything fails, your database remains in its previous state." — [Conflict Resolution](https://docs.turso.tech/sync/conflict-resolution), "Last Push Wins" and "What Happens During Pull". Note what last-push-wins means for this application: a losing writer's field values are overwritten with no signal, per statement, not per row-version.
- `@libsql/client` with `offline: true`: **Turso publishes no conflict-resolution documentation for this path at all.** The only primary source is the implementation, which is page-frame-level and *errors* rather than merging: `PushStatus::Conflict => return Err(SyncError::InvalidPushFrameConflict(frame_no, result.max_frame_no).into())` — [`libsql/src/sync.rs`](https://github.com/tursodatabase/libsql/blob/main/libsql/src/sync.rs), `SyncContext::push_frames`, with the error text "server returned a conflict: sent={0}, got={1}" (same file, `SyncError`). Recovery from that error is not documented anywhere I could find.

**Maturity caveat that gates the recommended answer.** `@tursodatabase/sync` runs on the Turso engine, not libSQL — "**Engine**: Turso (rewrite)" for `@tursodatabase/sync` versus "libSQL (SQLite fork)" for `@libsql/client` — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), package comparison table; and its remote URL is `turso://…` — [Turso Sync Usage](https://docs.turso.tech/sync/usage), Step 2. On the hosted platform that engine is preview: "Turso databases on Turso Cloud are in early preview — a reflection of how recently the offering landed on the platform, not of the engine itself. Create one with `turso db create --tursodb`." — [Turso Cloud](https://docs.turso.tech/turso-cloud), Note. The engine itself: "Turso Database runs in production today at multiple organizations. It has not yet reached 1.0, so as with any database we recommend keeping backups" — [`bindings/javascript/README.md`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/README.md), "About". By contrast, embedded replicas are "fully supported in production" — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), Info callout.

**Answer to the map's question, stated plainly:** offline writes are available, but not on the default embedded-replica configuration and not on the mature half of the product. Keeping the Constraint means either `@tursodatabase/sync` on a preview, pre-1.0 hosted engine with last-push-wins conflict semantics, or `@libsql/client`'s legacy `offline: true` with a conflict path that errors and has no published recovery story.

## 2 — Transactions over the remote protocol

**A batch stays atomic over the wire.** "A batch consists of multiple SQL statements executed sequentially within an implicit transaction. The backend handles the transaction: success commits all changes, while any failure results in a full rollback with no modifications." — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), "Batch Transactions". The mechanism is visible in the client: `executeHranaBatch` emits a `BEGIN <mode>` step, then each statement conditioned on `BatchCond.ok(lastStep)` and `not(isAutocommit)`, then a conditional `COMMIT`, then a `ROLLBACK` conditioned on the commit having failed — [`packages/libsql-client/src/hrana.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-client/src/hrana.ts), `executeHranaBatch`, lines 273–316. The whole thing is one HTTP request: "Pipeline all operations, so `hrana.HttpClient` can open the stream, execute the batch and close the stream in a single HTTP request." — [`packages/libsql-client/src/http.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-client/src/http.ts), `batch()`, line 174.

**The protocol is named Hrana, and it was designed for exactly this.** "To reduce the number of roundtrips, the protocol supports batches of statements that are executed conditionally, based on success or failure of previous statements. Clients can use this mechanism to implement non-interactive transactions in a single roundtrip." — [HRANA_3_SPEC.md](https://github.com/tursodatabase/libsql/blob/main/docs/HRANA_3_SPEC.md), "Overview". The batch primitive itself carries no transaction semantics — "A batch is represented by the `Batch` structure. It is a list of steps (statements) which are always executed sequentially. If the `condition` of a step is present and evaluates to false, the statement is not executed." — same document, "Batches". Atomicity is the client's `BEGIN`/`COMMIT` steps, not a protocol guarantee. Hrana runs over WebSocket or over HTTP (`POST /v2/pipeline`, statefulness carried by a `baton`) — [HRANA_3_SPEC.md](https://github.com/tursodatabase/libsql/blob/main/docs/HRANA_3_SPEC.md), "Hrana over HTTP"; [SQL over HTTP Reference](https://docs.turso.tech/sdk/http/reference), "`POST /v2/pipeline`".

**Interactive transactions are supported over the remote protocol, with a hard timeout.** `client.transaction(mode)` returns a handle with `execute()`, `commit()`, `rollback()`, `close()` — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), "Interactive Transactions". "Interactive transactions in libSQL lock the database for writing until committed or rolled back, **with a 5-second timeout**. They can impact performance on high-latency or busy databases." — same section, Warning. Over HTTP specifically: "Note that both transactions and connections have timeouts. Transaction have a 5 seconds window to complete, while connections get closed after 10 seconds of idle time." — [SQL over HTTP Reference](https://docs.turso.tech/sdk/http/reference), "Interactive query" Info.

**Against an embedded replica the behaviour differs, and it is documented.** "`write` / `BEGIN IMMEDIATE` — The transaction may execute statements that read and write data. **Write transactions executed on a replica are forwarded to the primary instance, and can't operate in parallel.**" and "`deferred` / `BEGIN DEFERRED` — The transaction starts in read mode, then changes to write as soon as a write statement is executed. **This mode change may fail if there is a write transaction currently executing on the primary.**" — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), "Transaction Modes". Note `deferred` is the default mode of `batch()` in `@libsql/client` ([`packages/libsql-client/src/http.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-client/src/http.ts), `batch(stmts, mode: TransactionMode = "deferred")`), so a batch left at its default can fail on that mode change. In the embedded-replica client the batch and transaction paths do *not* go through Hrana at all — they run local `BEGIN`/`COMMIT`/`ROLLBACK` through the native binding — [`packages/libsql-client/src/sqlite3.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-client/src/sqlite3.ts), `Sqlite3Client.batch()` lines 145–195 and `transaction()` lines 240–245.

**On the new stack, `batch()` defaults the other way.** "Without a `mode`, `batch()` is **not** transactional: each statement runs in its own autocommit step, so a failure mid-batch leaves earlier successful statements committed. With a `mode`, the batch becomes atomic — on the serverless driver the entire batch (including `BEGIN`, the user statements, `COMMIT`, and a conditional `ROLLBACK`) ships as a single Hrana request, so an atomic batch is still one round-trip." — [`docs/javascript-api-reference.md`](https://github.com/tursodatabase/turso/blob/main/docs/javascript-api-reference.md), "batch(statements, [mode])". Same page warns "Do not include transaction-control SQL (`BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`) in `statements`; the input is not validated". `@tursodatabase/sync` inherits this API — "db has same functions as Database class from @tursodatabase/database package but adds few more methods for sync" — [`bindings/javascript/sync/README.md`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/README.md), "Getting Started".

**Relevance to ADR 0027:** the shape survives. A batch remains the transaction on every transport examined — but the mode argument becomes load-bearing where today it is not, in opposite directions on the two stacks.

## 3 — The credential model

**Finer-grained than whole-database exists, and it is table-and-action, not row-level.** "Turso uses scoped, JWT-based tokens to control access to your databases. Every token can be restricted by database, permission level, and expiration." — [Authorization](https://docs.turso.tech/sdk/authorization), intro. The documented scoping levels are Group ("Access all databases in a group"), Database ("Access a single database"), Read-only ("Queries only, no writes"), Table + Action ("Specific tables and operations", `-p <table>:<actions>`), Time-limited (`--expiration 7d`) — same page, "Scoping Levels" table. Actions available: `data_read`, `data_add`, `data_update`, `data_delete`, `schema_add`, `schema_update`, `schema_delete`, with `all` usable as the table name — [Fine-Grained Permissions](https://docs.turso.tech/sdk/authorization/fine-grained-permissions), "Available Actions" and "Permission Format". One default worth knowing: "`data_read` is allowed on SQLite system tables (e.g., `sqlite_master`, `sqlite_schema`) by default" — same page, Note.

**Row-level scoping is not documented anywhere.** I searched the complete published documentation corpus (`https://docs.turso.tech/llms-full.txt`, 1.08 MB, fetched 2026-08-13) for `row-level`, `row level`, `RLS` and `per-row`: the only hits are unrelated (`per-row functions` in the SQL function reference). Recorded as an absence, not as a denial — Turso nowhere states that row-level scoping is unavailable.

**Expiry.** `-e, --expiration` takes `never` or a duration such as `7d` or `7d3h2m1s` — [db tokens create](https://docs.turso.tech/cli/db/tokens/create), "Flags" and "Create a token with a specific expiration time". The Platform API's `expiration` query parameter **defaults to `never`** — [Generate Database Auth Token](https://docs.turso.tech/api-reference/databases/create-token), OpenAPI `parameters.expiration.schema.default`.

**Revocation is bulk-only and rotates keys.** "You can invalidate all existing tokens for a database or group, which rotates the signing keys" — [Platform Tokens](https://docs.turso.tech/sdk/authorization/tokens), "Invalidating Tokens". The blast radius is wider than the database named: "All tokens in the group that provided database belongs will also be invalidated. This means that all existing tokens will no longer be valid and will need to be regenerated." — [db tokens invalidate](https://docs.turso.tech/cli/db/tokens/invalidate), Warning. **There is no documented way to revoke one database token.** (`/api-reference/tokens/revoke` revokes *Platform API* tokens — a different credential — [Turso Platform API](https://docs.turso.tech/api-reference/introduction) token endpoints.)

**How fast revocation takes effect is not stated.** The only timing statement is "A short downtime is required to complete the changes." — [Invalidate All Database Auth Tokens](https://docs.turso.tech/api-reference/databases/invalidate-tokens), Warning. No propagation figure, and nothing at all about what an already-connected embedded replica or an offline client does when its token is invalidated. Open.

**A documented inconsistency to be aware of when scoping tokens.** [Platform Tokens](https://docs.turso.tech/sdk/authorization/tokens) lists `-p, --permissions` as a flag of `turso db tokens create`, but the CLI reference page for that command — [db tokens create](https://docs.turso.tech/cli/db/tokens/create), "Flags" — lists only `-e/--expiration` and `-r/--read-only`. The Platform API is narrower still: its `authorization` parameter is an enum of exactly `full-access | read-only`, and its `CreateTokenInput` body carries only a `read_attach` permission object — [Generate Database Auth Token](https://docs.turso.tech/api-reference/databases/create-token), OpenAPI `parameters.authorization` and `schemas.CreateTokenInput`. So fine-grained permissions are documented for the CLI and for JWKS, and **not** for the Platform API endpoint an application would call to mint a per-user token programmatically. I did not run the CLI or the API to settle which page is stale.

**JWKS defaults are dangerous.** "If you don't setup a JWT template with specific permissions, the generated tokens will have access to **all databases in all groups** by default." — [External Auth Providers](https://docs.turso.tech/sdk/authorization/jwks), Warning. And "During the Turso Beta, we only support Clerk & Auth0 as OIDC providers." — same page, Info.

## 4 — Schema migrations against a hosted database

**The documented tooling is drizzle-kit, pointed at the remote.** `dialect: "turso"` with `dbCredentials: { url: TURSO_DATABASE_URL, authToken: TURSO_AUTH_TOKEN }`, then `drizzle-kit generate` and `drizzle-kit migrate` — [Drizzle + Turso](https://docs.turso.tech/sdk/ts/orm/drizzle), "Configure Drizzle Kit" and "Database migrations". This is the same `drizzle-kit generate` this repository already runs; only `migrate` moves. Prisma is worse off: "Prisma Migrate and Introspection workflows are currently not supported when working with Turso" — [Prisma + Turso](https://docs.turso.tech/sdk/ts/orm/prisma), "Database Migrations".

**One SQLite migration idiom does not survive.** "`user_version` — Read-only on Turso Cloud. Use a `_schema_version` table instead to track schema migrations." and "`journal_mode` — Not supported." — [Limitations](https://docs.turso.tech/cloud/limitations), "Pragma statements" table, with a worked `CREATE TABLE IF NOT EXISTS _schema_version` in the Warning below it.

**The feature built for schema-across-many-databases is deprecated.** Multi-DB Schemas propagated a parent schema to child databases — exactly the database-per-workspace shape — but: "This feature is now deprecated for all new users. Existing paid users can continue to use Multi-DB Schemas" — [Multi-DB Schemas (Deprecated)](https://docs.turso.tech/features/multi-db-schemas), Warning. Its mechanics, for reference if it is ever revived: dry-run across all associated databases first, then a migration job with a task per referencing database, then the parent last; "**During a migration, all databases are locked to write operations.**"; "You can't create or delete a database if there are any migrations running." — same page, "Things to know". Status is pollable at `GET /v1/jobs` with statuses `WaitingDryRun`, `DryRunSuccess`, `DryRunFailure`, `WaitingRun`, `RunSuccess`, `RunFailure` — [SQL over HTTP Reference](https://docs.turso.tech/sdk/http/reference), "Schema Migration Status"; that endpoint carries its own limit: "Currently not available on AWS for Free, Developer and Scaler plans." (same section, Warning).

**On clients at different schema versions, Turso says one sentence and pushes it to the application:** "Make sure any application querying the child databases handle any databases not yet updated with the schema." — [Multi-DB Schemas (Deprecated)](https://docs.turso.tech/features/multi-db-schemas), "Things to know". Beyond that sentence — which is scoped to a deprecated feature — **I found nothing addressing version skew between clients and a hosted database.** No guidance on an older client meeting a newer schema, no schema-version negotiation, no compatibility window. Open, and it is the whole of decision 06's question.

## 5 — Database-per-workspace at the service's limits

Plan quotas, from [Turso pricing](https://turso.tech/pricing), plan comparison table (all figures as published 2026-08-13):

| | Free | Developer | Scaler | Pro |
| --- | --- | --- | --- | --- |
| Databases | 100 | Unlimited | Unlimited | Unlimited |
| Storage | 5 GB | 9 GB (+$0.75/GB) | 24 GB (+$0.50/GB) | 50 GB (+$0.45/GB) |
| Monthly rows read | 500 M | 2.5 B | 100 B | 250 B |
| Monthly rows written | 10 M | 25 M | 100 M | 250 M |
| Monthly syncs | 3 GB | 10 GB (+$0.35/GB) | 24 GB (+$0.25/GB) | 100 GB (+$0.15/GB) |
| Point-in-time restore | 1 day | 10 days | 30 days | 90 days |

Every one of those is plan-dependent, and the quota set is confirmed by the Platform API's own schema — `rowsRead`, `rowsWritten`, `databases` (nullable, matching "Unlimited"), `locations`, `storage` (bytes), `groups`, `bytesSynced` — [List Plans](https://docs.turso.tech/api-reference/organizations/plans), OpenAPI `schemas.PlanQuotas`.

**Exceeding a quota blocks the databases, and blocks them across metrics.** "**Free plan, or paid plan with Overages disabled**: Yes. Once you exceed the limit on any single metric (storage, rows read, rows written, or syncs), your databases are blocked, even if the other metrics are still well under quota. **Paid plan with Overages enabled**: No." — [Turso pricing](https://turso.tech/pricing), FAQ "If I hit the limit on one metric, am I blocked from using the others?". The failure is surfaced as an error code: "any query that exceeds these limits will result in a failure, indicated by the `BLOCKED` error code" — [Usage & Billing](https://docs.turso.tech/help/usage-and-billing), Info callout.

**Database size is a user-set option, not a documented service cap.** `--size-limit` on `turso db create` is "The maximum size of the database in bytes. Values with units are also accepted, e.g. 1mb, 256mb, 1gb." — [db create](https://docs.turso.tech/cli/db/create), "Flags". Import from a file is capped: "The file size is limited to 2GB." — same page, "Create database from SQLite file" Info. **I found no per-database maximum size imposed by the service**; the binding constraint is the account-wide storage quota above.

**Groups gate the free tier.** "Creating more than one group is limited to Scaler, Pro and Enterprise plans." — [group create](https://docs.turso.tech/cli/group/create), Info. Note that a group is also the revocation blast radius (§3) — one group means one invalidation kills every workspace's token.

**No documented limit on concurrent connections.** I searched the full documentation corpus (`https://docs.turso.tech/llms-full.txt`, fetched 2026-08-13) for `concurrent connection`, `connection limit`, `max connections`: the only hit is unrelated advice about `nextval()` in WAL mode. The only concurrency figure anywhere is client-side and configurable: "By default, the client performs up to `20` concurrent requests" — [TypeScript Reference](https://docs.turso.tech/sdk/ts/reference), "Concurrency". Recorded as an absence.

**The unit that will actually bill a per-workspace deployment is rows read, and it is scans, not results.** "In SQLite, the term 'row read' actually refers to a 'row scan' during statement execution… Queries lacking index support perform a full table scan, incurring a row scan for each table row." — [Usage & Billing](https://docs.turso.tech/help/usage-and-billing), "Rows Read" and "Full Table Scans". Also: "Using functions like `count`, `avg`, `min`, `max`, and `sum` results in a row scan for every row considered in the aggregation" (same page), "Even if a transaction is not committed, any row that was inserted or updated during the transaction incurs a row write" (same page, "Implications of Aborted Transactions"), and "the `VACUUM` command… is currently disabled in Turso" (same page, "Total Storage" Note). Writes cost more than they look: "a single INSERT, UPDATE, or DELETE on a table with indexes counts as more than one row written, because each affected index also has to be updated" — [Turso pricing](https://turso.tech/pricing), FAQ "How are 'rows read' and 'rows written' calculated?".

**Sync bandwidth is billed in pages, and the embedded-replica unit is coarse.** "Embedded Syncs measure the amount of data, in pages, transferred between Turso Cloud and your local embedded database when syncing changes in either direction." — [Turso pricing](https://turso.tech/pricing), FAQ "How are 'Embedded Syncs' calculated?". "One frame equals 4kB of data (one on disk page frame), so if you write a 1 byte row, it will always show up as a 4kB write since that is the unit in which libsql writes with." — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), "Things to know", which also warns that a btree node split, a server restart with a dirty WAL, or deleting the local files can all sync far more frames than expected. Against the free tier's 3 GB/month that is roughly 750,000 page-frames across all devices.

## 6 — Read latency and payload

**An embedded replica's reads are local and not network-bound — that is the documented headline.** "reads run locally from the file in microseconds, and writes are sent to the cloud primary and then reflected back to the replica" — [Embedded Replicas](https://docs.turso.tech/features/embedded-replicas/introduction), Info callout; "enabling microsecond-level read operations" — same page, intro. A remote (non-replica) read is the opposite: "**Read latency** — SQL over HTTP: Network round-trip per query. In-Function SQLite: In-process SQLite read (zero network hops)"; "**Write latency** — Network round-trip" in *both* columns — [Vercel](https://docs.turso.tech/integrations/vercel), approach comparison table.

**No numeric read-latency figure is published.** "microseconds" and "network round-trip" are the whole of it; I found no percentile, no regional matrix, no benchmark in the documentation. Open.

**Write latency does have documented ceilings, and they are plan-dependent.** Added commit latency: Free up to 100 ms, Developer up to 50 ms, Scaler up to 25 ms, Pro and above up to 10 ms, all at 99.999999999% durability — [Durability Guarantees](https://docs.turso.tech/cloud/durability), table. "The commit latency is not the expected latency in every commit, but the **ceiling** of added latency in each commit" (same page, "Commit latency"), because "commits are batched across many databases to amortize" the cost of writing to object storage (same section). This is *added* latency on top of the network round trip, and it is per commit — which prices ADR 0027's one-batch-per-write directly, and prices the reconcile paths' one-`UPDATE`-per-row loops brutally if they ever run against a remote.

**No result-set or response-size cap is documented by Turso.** I searched the full corpus for `max_response`, `response size`, `RESPONSE_TOO_LARGE`, `too large`, `payload`: nothing. The open-source server that Turso Cloud reports itself as (`GET /version` returns e.g. `sqld 0.21.9` — [SQL over HTTP Reference](https://docs.turso.tech/sdk/http/reference), "`GET /version`") does enforce one, with these **defaults**: `SQLD_MAX_RESPONSE_SIZE` default `10MB` and `SQLD_MAX_TOTAL_RESPONSE_SIZE` default `32MB` — [`libsql-server/src/main.rs`](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/main.rs), CLI argument declarations; exceeding it produces "query response exceeds the maximum size of {}. Try reducing the number of queried rows." — [`libsql-server/src/query_result_builder.rs`](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/query_result_builder.rs), `QueryResultBuilderError::ResponseTooLarge`. **These are the open-source defaults, not a statement about Turso Cloud's configured values**, which are not published. Against ADR 0010's ~110 kB largest list and ~1.5 MB at 14× stress scale there is headroom either way, but the number is not a guarantee.

**Incremental result reading exists in the protocol and is deliberately unused by the HTTP client.** Hrana defines `open_cursor` / `fetch_cursor` so "the client can then use to read the results incrementally" — [HRANA_3_SPEC.md](https://github.com/tursodatabase/libsql/blob/main/docs/HRANA_3_SPEC.md), "Open a cursor executing a batch". `@libsql/client` skips it on purpose: "we do not use a cursor here, because it would cause three roundtrips" — [`packages/libsql-client/src/http.ts`](https://github.com/tursodatabase/libsql-client-ts/blob/main/packages/libsql-client/src/http.ts), `batch()`, line 183.

## Limitations

- **Nothing was executed.** No Turso account, no CLI invocation, no client run, no live request to any Turso endpoint. Every claim above is read from published documentation, published OpenAPI, or source in the vendor's own repositories. Where the CLI reference and the authorization guide disagree about the `-p` flag (§3), I did not settle it, because settling it means running the CLI.
- **Question 1's default is documented outright; its offline half is documented thinly.** "Writes are sent to the remote primary… They are NOT written to the local file first" is Turso's own sentence, not an inference. But **Turso publishes no page on what `offline: true` actually guarantees** — not on conflict resolution, not on what happens to a queued local write that cannot push, not on ordering, not on error recovery. What I report for that path (§1, conflict) is **read from `libsql/src/sync.rs` at `main`, not from documentation**, and it may not match the release `@libsql/client` 0.17.4 pins. Treat "an offline write that conflicts errors out with no documented recovery" as a code-derived claim with a version gap.
- **The `syncInterval`-dropped-in-offline-mode finding is code-only** (`libsql-js@v0.5.28`), was not tested, and contradicts no documentation because no documentation covers it. It is the kind of thing a prototype would confirm in ten minutes.
- **I did not verify that `@tursodatabase/sync` works against a libSQL (non-tursodb) Turso Cloud database.** The docs consistently show `turso://` URLs and describe the Turso engine; whether a `libsql://` database can be a sync target is not stated either way. This matters, because it decides whether choosing offline writes also means choosing the early-preview engine.
- **Not checked at all:** `sync/partial.md` (partial sync) beyond confirming it says nothing about transactions; branching; point-in-time recovery; private endpoints; BYOK encryption; allow rules; the AWS-vs-legacy-region split, which several warnings gate features on ("Currently not available on AWS for Free, Developer and Scaler plans") without defining which regions are which; audit logs; and the Go, Rust, Python, Swift and Kotlin SDKs except where the Rust crate was the primary source for a semantic.
- **Pricing figures were read from `turso.tech/pricing`, which is the vendor's own page and therefore primary, but it is a marketing page and carries no effective date.** Two of its FAQ answers (overages behaviour, blocking) were extracted from the page's embedded `FAQPage` JSON-LD, because the rendered accordions are collapsed; the text is verbatim from the page's own markup. Note also that [Usage & Billing](https://docs.turso.tech/help/usage-and-billing) still names "the Starter and Scaler plans" while the pricing page sells Free / Developer / Scaler / Pro — the docs page is stale, and I used the pricing page where they disagree.
- **`turso db create --tursodb`** is named in [Turso Cloud](https://docs.turso.tech/turso-cloud) but does not appear in the flag table of [db create](https://docs.turso.tech/cli/db/create). Another docs inconsistency I did not resolve.
- **No secondary source is load-bearing for any claim above.** Turso's blog is linked from its own docs twice (a sync bandwidth benchmark and a serverless deep-dive); I did not open either, and no claim here rests on them. Nothing was taken from a forum, a comparison article, or a third-party write-up.
- **Absences are reported as absences.** Where I say something is not documented — row-level scoping, concurrent-connection limits, per-database size caps, revocation propagation time, read-latency figures, response-size caps, client/schema version skew — that means a search of the complete published corpus (`https://docs.turso.tech/llms-full.txt`, 1.08 MB, fetched 2026-08-13) plus the relevant reference pages found nothing. It does **not** mean Turso states the thing does not exist.
