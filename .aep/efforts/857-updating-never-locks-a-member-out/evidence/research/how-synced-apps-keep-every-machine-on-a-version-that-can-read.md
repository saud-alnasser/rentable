# Question

When one member's machine updates rentable and upgrades a shared organization (format) or workspace (schema), how do mature synced, multi-device, local-first or offline-first apps keep the other machines working, or get them updated, with the least friction? Five sub-questions: who decides when a shared upgrade happens; whether the upgrade is deferred until every client can read it; how old clients are made to update; whether the reader ships before the writer; and what happens to an old client's unsent changes.

Asked by the human, 2026-10-07: "There should be a way to handle updates seamlessly; research before we make decisions." Researched 2026-10-07 against `main` at `faafc3a5` and the sources below. Builds on [[efforts/838-permissions-are-a-role-and-an-override/evidence/research/how-updates-migrate-and-fall-back]] (cited below as **R838**), which covers migration chains, atomicity, fallback, and the additive-only rule of Realm and PowerSync (its F4.1, F4.2). Those findings are not repeated.

**Round two, asked the same day.** The human: "what i want is that anyone can upgrade safely to the latest version and work with any workspace and org; but since some changes do migration to the database, should orgs and their workspaces have an update button or something; try to find the solution by research that makes it easy to upgrade my client and upgrade the org and workspaces by migration without causing older clients to be locked out." The human chose the minimum-reader floor (round one's option 1) as part of the answer. The target: (1) a newer build works against organizations and workspaces that have not been migrated; (2) migrating the data is an explicit act; (3) that act does not lock out older clients still in use, or at least lets whoever presses it see and avoid that. Findings F7 to F10 and the round-two conclusion answer it; round one is kept as it was.

# Findings

## 1. Who decides when the shared upgrade happens

**F1.1 source, Joplin: a person starts it, one client does it under an exclusive lock.** Sync locks are of two kinds: many `SYNC` locks, and one `EXCLUSIVE` lock "used when upgrading a sync target". "When a user initiates an upgrade", the client restarts into an upgrade screen and performs the upgrade (sync_lock spec). `MigrationHandler.upgrade` acquires the exclusive lock, refreshes it while it walks `migrations[from+1 .. to]`, and releases it. A client older than the target throws `outdatedClient`: "Sync version of the target (%d) is greater than the version supported by the app (%d). Please upgrade your app." A client newer than the target throws `outdatedSyncTarget`: "... Please upgrade the sync target." (`MigrationHandler.ts`). **interpretation:** Joplin's structural upgrade is rentable's workspace path with a person in the loop: the target does not move until a human presses the button.

**F1.2 source, Joplin: a second gate that the first new client raises without asking.** Separately from the sync-target version, `info.json` carries `appMinVersion`. The code comment says it "should be set to the client version whenever we require all the clients to be at the same version in order to synchronise", giving as the example the trash feature, where an old client syncing with a new one would no longer delete notes, and "Usually this variable should be bumped whenever we add properties to a sync item." `localSyncInfo()` writes the running build's `appMinVersion_` (`'3.7.0'` at reading) into the info it syncs, and `checkIfCanSync` refuses an older app with "In order to synchronise, please upgrade your application to version %s+" (`ErrorCode.MustUpgradeApp`) (`syncInfoUtils.ts`). **interpretation:** for feature-level changes, Joplin is "first client to update decides", which is what rentable does for a workspace; Joplin keeps it to changes where an old client would corrupt meaning, not to every additive change.

**F1.3 source, Anki: a data feature turned on, then old clients told by name.** The collection's metadata carries flags (`v2_scheduler_or_later`, `v2_timezone`) derived from the collection's settings; the server compares them with the client's declared `sync_version` and stops the sync with "Your client does not support the v2 scheduler" or "Your client does not support the new timezone handling." The protocol versions are commented with their dates and, for v8, the share of syncers still on it at the end of 2022 (0.045%) (`meta.rs`, `version.rs`). **interpretation:** Anki gates on the *feature in use*, not the app version, so an old client keeps syncing until the user actually enables the feature it cannot read.

**F1.4 source, Ditto: the developer opts in after the fleet has moved, and the cut spreads.** `disableSyncWithV3()`: "Explicitly opt-in to disabling the ability to sync with Ditto peers running any version of the SDK in the v3 (or lower) series ... Note that this disabling of sync spreads to peers that sync with a peer that has disabled, or has (transitively) had disabled, syncing with v3 SDK peers." (Ditto 4.0.2 reference). **interpretation:** the breaking switch is separated from shipping the code that can run past it; it is an explicit later act.

**F1.5 source, Firefox Sync: no gate at all.** "We must not break 'recent' Firefox installations when a 'new' Firefox installation syncs, and vice-versa." The accepted policy: fields cannot change type or be removed "for significant periods", and "Every sync engine must arrange to persist any fields from the payload which it does not understand" and add them back when it uploads. Formal schema versioning that would stop older clients syncing was considered and **rejected**, because it would "penalize users who chose to use Nightly" and "effectively break Release/Mobile Firefox versions" (payload-evolution, 2023-03-15).

**F1.6 source, servers with a window.** Zero keeps `minSupportedVersion` and `maxSupportedVersion` in a `schemaVersions` table; a backend "expand" migration raises the max, the client ships with its `schemaVersion`, and the min is raised later in the contract step (**search summaries only**). Replicache's `onUpdateNeeded` fires when "the server no longer supports the pushVersion, pullVersion or schemaVersion of the current code", and by default reloads the page (Replicache reference). Bitwarden publishes a window: each server version "is compatible with clients of the same major version, the previous 2 major client versions, and the subsequent 2 major client versions" (Bitwarden). **interpretation:** where a server exists, the window lives on the server and the operator moves it. Rentable has no operator-run server; the nearest equivalent places are the organization database and the GitHub `latest.json`.

**F1.7 interpretation, the pattern across F1.1 to F1.6.** Two gates appear again and again, and they are kept apart: a *structural* version that changes what can be read at all (Joplin sync target, Anki full sync, Ditto major series), moved rarely and by an explicit act; and a *minimum reader* that changes only when an old client would misread or corrupt data (Joplin `appMinVersion`, Zero `minSupportedVersion`, Anki feature flags). Additive change moves neither (Firefox Sync, Joplin's "usually bumped when we add properties" being the exception it names). Rentable has one number per database and refuses on any increase (F5.1).

## 2. Deferring the upgrade until every member can read it

**F2.1 source and absence.** Of the sources read, the ones that defer a shared change until clients can read it do it by an operator moving a window (Zero, F1.6) or a developer opting in later (Ditto, F1.4). Firefox Sync defers indefinitely by never breaking (F1.5). **No source read records each client's app version in the shared data and holds an end-user-triggered upgrade until every recorded client is new enough.** Signal's server knows client versions (it disables an old API "90 days after the release", per its support pages, **search summary only**) and Replicache's server sees `schemaVersion` on every push and pull, but both use it to refuse, not to hold an upgrade. This absence is a finding; it means option B below has no direct precedent in what was read.

**F2.2 source, how the wait is surfaced.** Joplin surfaces it as an error on the client that cannot proceed, with the version it needs (F1.1, F1.2). Anki surfaces it as a server message on sync (F1.3). Nothing read shows the *upgrader* a list of who would be locked out.

## 3. Making old clients update with low friction

**F3.1 source, Signal Desktop: a build that expires, plus a remote minimum.** Each build is stamped at packaging with `buildExpiration = buildCreation + 90 days` (30 days for builds that cannot update) (`get-expire-time.mjs`). If the user has turned off automatic download, the local expiry is 60 days earlier (`getBuildExpirationTimestamp`). Remote config key `desktop.clientExpiration` holds a list of `{ "min-version", "iso8601" }`; when `min-version` is above the running version, its date becomes the expiry if it is earlier; a successful fetch without the key clears it (`RemoteConfig.dom.ts`, `parseRemoteClientExpiration.dom.ts`). `BuildExpirationService` emits `expired` when the time comes. **interpretation:** a minimum version with a *deadline*, published from somewhere the vendor controls, is the gentlest forced update read: old builds keep working until a date, not until the moment someone else upgrades.

**F3.2 source, Sparkle (macOS).** `<sparkle:criticalUpdate>` items "are shown to the user more promptly and do not let the user skip them", optionally only for versions below a given one. `sparkle:minimumAutoupdateVersion` is "the lowest version that can automatically update" to this one; below it the user always sees the UI. `sparkle:informationalUpdate` shows a link instead of installing. `phasedRolloutInterval` spreads an update over seven groups; "Critical updates and manual checks bypass phasing." (Sparkle publishing). **interpretation:** the "required" flag lives in the update feed itself, beside the version.

**F3.3 source, Electron.** After `checkForUpdates()`, "If an update is available it will be downloaded automatically", and "A successfully downloaded update will always be applied the next time the application starts", whether or not `quitAndInstall()` is called (Electron `autoUpdater`).

**F3.4 source, Tauri updater (the plugin rentable uses).** `check()` returns an update; `download()` and `install()` can be called separately rather than `downloadAndInstall()` (Tauri docs). On Windows "the application automatically exits when installation begins" (`std::process::exit(0)` after launching the installer, with an `on_before_exit` hook); macOS replaces the `.app` bundle in place and Linux AppImage swaps the executable, so neither needs to exit, and relaunching is the app's call through the process plugin's `relaunch()` (docs, `updater.rs`). Windows install modes map to installer flags: `passive` to NSIS `/P` and msiexec `/passive` ("only shows a progress bar"), `quiet` to `/S` and `/quiet` ("Requires admin privileges if the installer does"), `basicUi` to msiexec `/qb+`; `passive` and `quiet` also pass NSIS `/R`, restart after install, controlled by `restart_after_install` (default `true`) (`config.rs`, `updater.rs`, crate 2.13.1). The manifest's required fields are `version`, `platforms.<target>.url` and `.signature`, with optional `notes` and `pub_date`; the whole response is kept as `raw_json`, so an app can read fields of its own (`updater.rs`). **The Tauri docs read say nothing about required or minimum-version updates, and nothing about installing on quit.** **interpretation:** a "download in the background, install when the user next quits or relaunches" flow, and a "required" flag, are both buildable on Tauri but are application code, not plugin features. On Windows, install-on-quit means running `install()` from an exit path, which the plugin's own exit fits.

**F3.5 source, platform guidance on required updates.** Android: flexible updates are for when "it's acceptable for the user to use the app while downloading"; immediate updates are "fullscreen UX flows that require the user to update and restart the app in order to continue using it ... best for cases where an update is critical to the core functionality of your app" (Android in-app updates). Microsoft: a Store package can be marked mandatory from a date; "The mandatory status of a package update is not enforced by Microsoft, and the OS does not provide a UI"; the app "can disable features", and should "downgrade your app experience gracefully" if the mandatory update fails; silent download and install exist but succeed only with the user's automatic-update setting on and off a metered network, and the sample installs only when `IsNowAGoodTimeToRestartApp()` (Microsoft Learn). **Apple's HIG was searched for guidance on required update prompts and none was found;** the only Apple-hosted hits were developer-forum threads, which are not guidance.

## 4. Shipping the reader before the writer

**F4.1 source, Joplin backports the reader.** "2026-07-10: Joplin 3.6 now supports the Joplin 3.7.0 sync format. This allows the 3.6 stable release to sync with clients that have been upgraded to Joplin 3.7." `checkIfCanSync` lets an app below `appMinVersion` sync when `appMinVersion` equals the known forward-compatible value `'3.7.0'` *and* the target uses no feature the older app cannot honour (`noteLockKey` is null); otherwise it refuses as before. `localSyncInfo` keeps `appMinVersion` from being lowered in that mode "to avoid data loss" (`syncInfoUtils.ts`). **interpretation:** this is "reader ships before writer" done after the fact, with a second check for the one feature the backport cannot read. Its cost is visible in the code: a named constant, a carve-out in the gate, and a guard against an older client lowering the floor.

**F4.2 source.** Zero's order is "deploy the server first before deploying the client" for additive changes (**search summary**); Ditto ships v4 able to talk to v3 and leaves the cut to a later opt-in (F1.4); Anki's feature flags let a client that knows the feature ship long before anyone turns it on (F1.3). Expand and contract (R838 F1.9) is the same idea applied to schema.

**F4.3 interpretation.** Every instance found pairs the early reader with a *separate* switch that turns the new writing on later: a person's choice (Anki, Joplin's target upgrade), a developer opt-in (Ditto), an operator raising a window (Zero). None found ties the switch to "the first client that happens to run the new build", except Joplin's `appMinVersion`, which is the case Joplin then had to soften (F4.1).

## 5. What happens to an old client's unsent changes

**F5.1 source.**
- Anki: before a change that forces a full upload, the user is asked: "If you have reviews or other changes waiting on another device that haven't been synchronized here yet, they will be lost. Continue?" (`qt-misc.ftl`). Lost, with consent.
- Realm: client reset recovers unsynced changes by default, but not when the client app has breaking schema changes or recovery mode is off on the server (**search summary**). Lost on a breaking change.
- Replicache: a new instance recovers another instance's pending mutations, but "it does not migrate any unsent mutations across versions" (v9.0.0-beta.1 notes; true of that release, later releases not checked).
- Joplin: an old client is refused before any sync (F1.1, F1.2), so its local changes stay in its own database; whether they sync after it updates was **not verified** in code.
- Firefox Sync: an old client keeps syncing, and round-trips fields it does not know (F1.5). Nothing is lost.

**F5.2 interpretation.** Only the systems that never lock the old client out (Firefox Sync), or that refuse it *before* it can write against the new shape (Joplin), keep its changes without translation. The rest drop them, warn first (Anki), or recover them only for non-breaking changes (Realm).

## 6. Rentable, measured against the above

**F6.1 observation, one gate per database, on any increase.** `lease/apply.rs` refuses with `WorkspaceNewer` whenever the recorded `at > up_to`, with the message "the workspace was upgraded by a newer rentable (schema {at}, and this one knows {up_to}). update rentable to open it; nothing was changed". The organization path does the same with `OrganizationNewer` (`error.rs`). **interpretation:** the rule `.aep/rules/migrations.md` already demands add-before-remove, but the gate refuses an older build on *any* newer number, so an additive workspace migration takes older builds off the workspace exactly as a destructive one would. Expand and contract as written buys data safety, not continued access. This is the main gap against F1.5, F1.7 and F4.

**F6.2 observation, the shared upgrade is triggered by whoever opens first.** A workspace moves when the first full-access member opens it under a newer build (the brief; the lease in `apply.rs`). The organization's format moves only on the owner's machine (`OrganizationOlder` "waits for its owner to open it in this version", `error.rs`). **interpretation:** the organization path is Joplin's target upgrade minus the explicit button (F1.1); the workspace path is Joplin's `appMinVersion` (F1.2).

**F6.3 observation, a machine registry already exists.** The organization holds `machine` (`id`, `member_id`, `seen_at`, `created_at`), and "every machine that is running refreshes its row at every launch" (`MACHINE_PRESENCE_WINDOW`, seven days). `machine_name` is written by each machine alone, and "The row standing is what says the machine runs a build that reads `machine_sign_out`" (`session.rs`). **interpretation:** rentable already uses a row's presence as a capability signal, which is a primitive form of recording what each machine can read; adding the build version or the highest schema and format a machine can read is a small extension of a pattern already in the code. Because `machine` is rewritten whole at launch and merges last-push-wins per column (the `MACHINE_SIGN_OUT` comment), a value written only by its own machine fits.

**F6.4 observation, updates.** `tauri.conf.json` points the updater at `https://github.com/saud-alnasser/rentable/releases/latest/download/latest.json` with `installMode: "passive"`; `Cargo.toml` pins `tauri-plugin-updater = "2.10.0"`. The update check is a mutation (`query.ts`, `router.ts`), i.e. user-triggered; the host already maps `rawJson` (`host.ts`, `tauri.ts`), so a custom field in `latest.json` is readable without plugin changes. The brief also states (not re-verified here) that the refusal sentence is shown only in some places, never with an update action, and the app does not re-check after a pull.

## 7. One build, a range of data versions (round two)

**F7.1 source, Git: a small integer plus named extensions.** Format 0 is "the format defined by the initial version of git". Format 1 is identical except that Git "MUST also read any configuration keys found in the `extensions` section", and "If a version-1 repository specifies any `extensions.*` keys that the running git has not implemented, the operation MUST NOT proceed." Git says it prefers not to bump the repository version, and instead to bump "format version numbers of individual data files (e.g., index, packfiles, etc). This restricts the incompatibilities only to those files", and to introduce "new data that gracefully degrades when used by older clients (e.g., pack bitmap files are ignored by older clients...)" (repository-version). Extensions listed today include `objectFormat`, `refStorage`, `partialClone`, `preciousObjects`, `worktreeConfig`, `relativeWorktrees` and `submodulePathConfig`; `objectFormat` and `refStorage` "should only be set by git-init or git-clone" (extensions.adoc). **interpretation:** a current Git still opens a format-0 repository; a new build supports every old data version because each new thing is opt-in per repository.

**F7.2 source, Mercurial: a list of requirements.** `.hg/requires` holds one capability per line; an older Mercurial meeting one it does not know aborts with "abort: requirement 'dotencode' not supported!". Each requirement is dated to the release that introduced it (`revlogv1` 0.9, `store` 0.9.2, `fncache` 1.1, `dotencode` 1.7). The file is "completely unrelated to how this information is transferred over the wire" (RequiresFile wiki). **interpretation:** like Git's extensions, a new Mercurial reads an old repository as it is; nothing upgrades it implicitly.

**F7.3 source, SQLite: separate read and write versions.** Header bytes 18 and 19 hold a write version and a read version: where "the read version is 1 or 2 but the write version is greater than 2, then the database file must be treated as read-only", and where "a read version greater than 2 is encountered, then that database cannot be read or written." The schema format number (1 to 4) records what the file uses, each readable from a named SQLite release, and `SQLITE_DBCONFIG_LEGACY_FILE_FORMAT` makes new files in format 1 (fileformat2). **interpretation:** SQLite has a third outcome between "works" and "refused": an older reader may *read* data it must not *write*. That fits rentable's floor directly: an older build below the write floor but at or above a read floor could open a workspace read-only instead of being shut out.

**F7.4 source, Signal-Server: capabilities combined across an account's devices.** Each device reports capabilities; an account's capability is computed by mode: `PRIMARY_DEVICE`, `ANY_DEVICE`, `ALL_DEVICES` ("The account will have the capability iff all devices on the account have the capability"), or `ALWAYS_CAPABLE` ("supports retiring capabilities where older clients still need the field provided"). Per capability, `preventDowngrade` stops a device without it from linking once the account has it, and `requireForNewDevices` refuses to create a device that lacks it. `Account.hasCapability` implements the modes (`DeviceCapability.java`, `Account.java`). **interpretation:** this is the closest precedent found for the human's point (3): a feature that would break an old device turns on only when every linked device can handle it, and once it is on, an old device cannot join.

**F7.5 interpretation, a capability list against one integer.** One integer (rentable's workspace `schema_version` and organization `format`, Joplin's sync target) is simple to compare and forces a total order: any change, however small, moves every client. A list (Git extensions, Mercurial requires, Signal capabilities, Anki's flags in F1.3) lets each change gate only the clients it affects, and lets a new build support any combination, at the cost of testing combinations and of a name for every change. A floor (round one's option 1) sits between them: one integer for "what this database is", another for "the oldest that may read it", and optionally a third for "the oldest that may write it" (F7.3).

## 8. The explicit data upgrade (round two)

**F8.1 source, Joplin.** Desktop banner: "The sync target needs to be upgraded before Joplin can sync. The operation may take a few minutes to complete and the app needs to be restarted. To proceed please click on the link." (`MainScreen.tsx:585`); mobile: "The sync target needs to be upgraded. Press this banner to proceed." and a screen titled "Sync Target Upgrade"; CLI: "Upgrade the sync target to the latest version." (`command-sync.ts:41`). Any client of the account can press it; the upgrade runs under the exclusive lock (F1.1). An older app is told "In order to synchronise, Please upgrade your application to version %s: %s", with variants for a package manager and for "Joplin could not check update information" (`MainScreen.tsx:635` to `655`). **No string found warns the person pressing that other clients will be stopped.**

**F8.2 source, Anki.** The upgrade is triggered by the user changing something that needs it; the prompt names the cost on *other devices*: changes "waiting on another device that haven't been synchronized here yet ... will be lost. Continue?" (`qt-misc.ftl`).

**F8.3 source, Git and Mercurial: look first, then run.** `git refs migrate --dry-run` will "Perform the migration, but do not modify the repository. The migrated refs will be written into a separate directory that can be inspected"; its listed limitations include "There is no way to block concurrent writes ... Users are expected to block writes on a higher level" (git-refs). Mercurial's `debugupgraderepo` without `--run` prints "performing an upgrade with \"--run\" will make the following changes:" with the requirements, optimisations and affected revlogs; with `--run` it prints the same list, then takes the repository's locks ("repository locked and read-only"), upgrades into a temporary repository, swaps it in, and reports "copy of old repository backed up at %s" (`upgrade.py`).

**F8.4 source, Ditto.** The cut is an API call a developer makes, not an end-user action, and it spreads to peers transitively (F1.4).

**F8.5 interpretation.** The explicit-upgrade UIs found show *what* will change (Mercurial, Git) or *what may be lost* (Anki), and lock out concurrent writers while they run (Joplin, Mercurial). None found shows *who* will be locked out, except by implication in Signal, where the server simply waits for every device (F7.4). Showing named members and machines before the press would be rentable's own design, built from the pieces above.

## 9. Floor plus explicit upgrade: knowing who is behind (round two)

**F9.1 source.** Signal records capabilities per device and combines them (F7.4). Signal also unlinks devices that stay away: a linked device after 45 days of inactivity, and all linked devices if the primary phone stays offline more than 30 days (**search summary only** of support.signal.org). **interpretation:** the "all devices" rule only works because inactive devices fall out of the set.

**F9.2 observation, rentable's existing pieces.** Each running machine rewrites its `machine` row at every launch, and the seven-day `MACHINE_PRESENCE_WINDOW` already decides who counts as connected; `machine_name` is written only by its own machine and is already read as "this machine runs a build that reads `machine_sign_out`" (F6.3). A row of the same kind, written by each machine alone, holding the highest workspace schema and organization format its build reads and writes (and its build version, for the message), gives the pressing user the list. Machines older than this addition write no row; the absence itself says "older than the build that records this", as `machine_name` does today.

**F9.3 interpretation, machines not seen recently.** The sources offer three treatments: drop them from the set after a window (Signal, F9.1); ignore them and let them meet a refusal on return (Joplin, F1.1); or never lock them out because nothing breaks (Firefox Sync, F1.5). For rentable, the existing seven-day window is the obvious divider: machines seen inside it are listed as "will stop working until updated"; machines outside it are listed apart as "not seen since <date>", and on return they meet the refusal with an update action (round one, option 2).

## 10. The cost for rentable of running against older data (round two)

**F10.1 observation, both gates refuse in both directions today.** The organization gate is exact equality: `refuse_another_format` lets through only `Some(FORMAT_VERSION)` and returns `waits_for_its_owner()` (`OrganizationOlder`) for anything lower, so a newer non-owner build is refused against an organization its owner has not upgraded yet (`store/format.rs`). On a workspace, a newer build with full access migrates it on open, and a read-only one is refused with `WorkspaceBehind` (`error.rs`). **interpretation:** target (1) is not met today in either direction: a member who updates first is locked out until somebody else acts (organization), or upgrades the data without choosing to (workspace).

**F10.2 observation, the frontend assumes the latest columns.** Workspace queries run through drizzle (`drizzle-orm ^0.45.2`, sqlite-proxy) over one `schema.ts` describing the newest schema (`client.ts`). Run locally against the installed drizzle, a bare `select().from(payment)` produces `select "id", "direction", "note" from "payment"`, and an insert naming only `id` produces `insert into "payment" ("id", "direction", "note") values (?, ?, null)`: **both name every column the schema declares.** So a newer build's reads *and* writes fail with "no such column" against a workspace one migration behind, whenever the missing column belongs to a table the query touches. The other direction is kinder: an older build's statements name only the columns it knows, so they succeed against a newer workspace whose added columns are nullable or defaulted (`0005` adds three nullable columns; `0006` adds `direction ... DEFAULT 'received' NOT NULL`). There are 157 `.select(` calls in 31 non-test files under `src/lib`, and 54 insert or update calls.

**F10.3 observation, how often the data version moves.** Seven releases shipped between 2026-09-23 (`0.14.0`) and 2026-10-07 (`0.20.0`). The workspace schema changed in two of them (`0.16.0`: sixth file; `0.20.0`: `0006`), and the organization format reached 3 in `0.16.0`/`0.17.0`. The seven workspace files are dated 2026-03-08 to 2026-10-06 in drizzle's journal, five of them since 2026-08-04.

**F10.4 observation, what the recent changes were.** Workspace `0004` adds an index; `0005` adds three nullable `payment` columns; `0006` adds `payment.direction`. Format 2 to 3 "adds `workspace_override` and touches nothing else" (`overriding.rs`), and effort 846 added two more tables to format 3 "with no change of its own" (`install_format_three`). Format 1 to 2 re-signs every row into a chain of certificates (`chain/`); `0003` rebuilds seven tables. **interpretation:** most recent changes are additive in *shape*, but two change *meaning* for an older reader. A build that does not know `direction` counts a refund as money received; a build that does not know `workspace_override` grants a member more than the override allows. Those are Joplin's trash case (F1.2): additive, yet each must raise the floor. Only `0004` and `0005` would have left it where it was.

**F10.5 interpretation, a rough per-release cost of supporting one version back.** For a release that adds a column or table, keeping the build working against the previous workspace version means: the new feature is gated on the workspace's recorded version (hidden or offered as "upgrade this workspace to use it"); every query touching the changed table either selects named fields or uses a second table description without the new column; inserts omit the new column; and each router touched is tested against the seeded database of the previous version, which `.aep/rules/migrations.md` already requires to exist. For `0006` that is the payment queries and the figures that read `direction`, about two dozen non-test files by a rough grep for `direction` and `'refund'` (some unrelated). That suggests **one to three days per additive release**, mostly in tests. For a reshape like `0003` or format 1 to 2, carrying both shapes means two code paths through the feature; the realistic alternative is that this build reads the older data read-only, or offers the upgrade before writing (F7.3). For the organization, format 2 to 3 is cheap to tolerate (a missing `workspace_override` table reads as "no overrides"), and format 1's row judge is already kept in `upgrade/format/signature.rs` for the upgrade, though the runtime verifier does not use it. **interpretation:** a support window of **one version back** for additive changes is realistic at rentable's pace; more than one multiplies the test matrix every release. The sources' windows are larger only where change is rare or a server translates: Bitwarden supports two major versions either side (F1.6), Firefox Sync keeps fields "for significant periods" (F1.5), and Zero keeps a min to max range that an operator moves (F1.6, search summary).

# Conclusion, round one

**The evidence separates two things rentable has as one.** Mature synced apps keep a *structural* version, moved rarely and by an explicit act, apart from a *minimum reader*, raised only when an old client would misread data; additive change moves neither (F1.7). Rentable refuses on any newer number (F6.1), so its own add-before-remove rule does not keep older builds working. Separately, nobody read lets "the first machine that happens to update" lock others out without either a person choosing it (Joplin target, Anki), a deadline (Signal), or a reader already shipped (Joplin 3.6, Zero, Ditto).

Options for rentable, ranked as the researcher's reading of the evidence. **The choice is the human's.**

1. **C. A minimum-reader floor, so additive steps do not lock anyone out** (with the reader shipped a release ahead for anything non-additive). Each workspace migration and format step declares the oldest schema or format that can still read and write it safely; the database records that floor next to the version, and a build refuses only when its known version is below the floor, not below the version. Additive steps leave the floor where it was; a destructive step raises it, and per the existing rule ships a release after the expand. *Buys:* most updates stop locking anyone out at all. *Cost:* moderate: one more recorded number per database (workspace `schema_version` row and organization `format` row), a per-step floor in `migrate.rs` and `transition/`, changes to the two refusal checks, and tests that an older build writes safely against a newer additive schema (old inserts must not miss NOT NULL columns without defaults). *Risk:* an "additive" step that changes meaning (Joplin's trash example, F1.2) must raise the floor; getting that call wrong lets an old build write wrong data. *Sources:* Firefox Sync (F1.5), Joplin `appMinVersion` and its 3.6 backport (F1.2, F4.1), Zero min/max (F1.6), Anki flags (F1.3).
2. **A+D. Refuse and guide to update, made cheap: a refusal that carries an "Update now" action, background download, install on relaunch or quit, and a check after any refusal and at launch.** *Buys:* the locked-out member is one click and one restart from working, and usually already has the update downloaded. *Cost:* small to moderate, all frontend plus the updater's `download()`/`install()` split (F3.4); Windows exits on install, so install-on-quit runs from the exit path. *Risk:* still a hard stop at the moment someone else upgrades; an offline machine cannot fetch the update; silent installs need care with the passive installer's restart flag. *Sources:* Electron (F3.3), Sparkle (F3.2), Android immediate updates (F3.5), Microsoft mandatory (F3.5), Joplin and Anki messages (F1.1, F1.3). This is complementary to every other option, not an alternative.
3. **B. Record each machine's readable version in the organization and warn the upgrader (or hold the upgrade) while a recently seen machine cannot read the result.** *Buys:* no surprise lock-outs; the person upgrading sees who will be affected. *Cost:* small to record (extend the `machine` pattern, F6.3), moderate to surface and to decide what "hold" means for the workspace path, where today the upgrade is automatic on open. *Risk:* a machine unseen for weeks either blocks everyone or is ignored, so it needs the seven-day presence window or similar; **no precedent was found for holding an end-user-triggered upgrade on recorded client versions (F2.1)**, so the design would be rentable's own. *Sources:* nearest are Joplin's explicit target upgrade (F1.1), Ditto's opt-in cut (F1.4), Bitwarden's published window (F1.6).
4. **E. A minimum version with a deadline in `latest.json`.** A custom field (for example a minimum version and a date) in the release manifest, read from `rawJson`, after which an older build shows a blocking update screen. *Buys:* old builds are moved on before any data cut, on the developer's schedule rather than on a peer's. *Cost:* small (F6.4). *Risk:* it pushes updates for *all* users at once regardless of their organization; an offline machine never sees the field; it does not by itself stop a peer from upgrading the shared data sooner. *Sources:* Signal `desktop.clientExpiration` (F3.1), Sparkle critical updates (F3.2), Microsoft mandatory from a date (F3.5).

**Which unsent changes survive** depends mostly on option 1: where an older build keeps working (Firefox Sync) or is refused before it writes (Joplin), nothing is lost; rentable's `OrganizationChangesUnsendable` today is the drop that Anki at least asks consent for (F5.1, F5.2).

Confidence: high on what Joplin, Anki, Signal, Ditto, Firefox Sync, Sparkle, Electron and the Tauri plugin do (their source or reference docs, read 2026-10-07). Medium on Zero and Realm (search summaries). The ranking is interpretation.

# Conclusion, round two

**The human's target is what Git, Mercurial and SQLite do with their file formats, plus what Signal does across an account's devices.** A new build opens old data as it is (F7.1, F7.2). The data moves forward only by an explicit act that shows what will change and locks out concurrent writers while it runs (F8.3). Old readers are protected by a recorded floor, with a read-only middle state (F7.3). A change that would break an old device waits until every recently active device can take it (F7.4, F9.1). No single source does all four. Two parts are rentable's own: the list of named members and machines shown before the press (F8.5), and treating machines outside the seven-day window apart (F9.3).

**What it costs.** The main cost is target (1), not the button. Drizzle names every column of the newest schema in reads and writes (F10.2), and both gates refuse in both directions today (F10.1). A support window of one data version back, for additive changes, is realistic at about one to three days per additive release. A reshape cannot practically be carried both ways, and needs read-only access or the upgrade first (F10.5). Most recent "additive" changes still raise the floor because they change meaning (`direction`, `workspace_override`, F10.4). So the floor will often rise, and the "who is behind" list is what makes pressing the button safe.

**Three end-to-end designs, ranked as the researcher's reading of the evidence. The choice is the human's.**

**1. Floor, explicit Upgrade, and a who-is-behind check.** This meets all of (1), (2) and (3).
- *What the person sees.* Data a newer build can run on but has not migrated shows a quiet line on the workspace or organization: "Upgrade available". Features that need the new version are offered as "Upgrade this workspace to use refunds" rather than hidden. Pressing it shows the steps (Mercurial's list). If any step raises the floor, it also lists members' machines seen in the last seven days whose recorded version is below the new floor ("Sara's laptop, rentable 0.19, will need updating"), and separately the machines not seen since a date. The choices are "Upgrade now" and "Not yet".
- *Who can upgrade.* The workspace: a member with full access, as today's lease allows. The organization: the owner only, since the format walk needs the owner's keys (as today).
- *What older clients experience.* Additive steps that do not raise the floor leave them untouched. After a floor-raising upgrade, a machine at or above the read floor opens the data read-only (SQLite's split). Below that, it gets a refusal with "Update now", plus background download and install on relaunch (round one, option 2).
- *What it costs.* Large, once: a per-machine readable-version row (the `machine_name` pattern), a floor and an optional read floor next to `schema_version` and `format`, the two gates rewritten as ranges, an Upgrade surface for each database, and a lease or lock held for the walk. Then one to three days per additive release for the one-version-back window (F10.5).
- *Risks.* The read-only middle state is new code on every write surface. A misjudged "meaning" change lets an old build write wrong data. Machines that never launch the recording build show as unknown.
- *Sources.* Git, Mercurial and SQLite (F7.1 to F7.3), Mercurial and Git dry runs (F8.3), Signal `ALL_DEVICES` and inactivity (F7.4, F9.1), Joplin's banner and lock (F8.1).

**2. Explicit Upgrade with a one-version-back window, no recorded versions.** This meets (1) and (2), and only partly (3).
- *What the person sees.* The same "Upgrade available" line and step list. Instead of named machines, a generic warning when the floor rises: "Members on an older rentable will need to update before they can open this workspace."
- *Who can upgrade.* As in design 1.
- *What older clients experience.* As in design 1, without the read-only middle state unless it is added.
- *What it costs.* Moderate: the floor, the range gates, the Upgrade surface, and the per-release window cost. No per-machine record.
- *Risks.* The person pressing cannot see who they would stop. That is Joplin's position today (F8.1), and the evidence suggests it is the source of surprise lock-outs.
- *Sources.* Joplin (F1.1, F8.1), Anki's warning (F8.2), Git and Mercurial (F7.1, F7.2).

**3. Automatic once everyone can read it, with Upgrade as an override.** This meets (1) and (3), but makes (2) optional rather than the rule.
- *How it works.* Each machine records its readable version as in design 1. A floor-raising step runs on its own, on the first full-access machine (or the owner's, for the organization), once every machine seen in the window records that it can read the result. Until then, the "Upgrade" action stays available with the who-is-behind list. Additive steps that do not raise the floor run automatically.
- *Costs and risks.* Close to design 1's cost. It drifts from the human's stated wish that migration be deliberate. One dormant machine inside the window holds everyone back for up to seven days.
- *Sources.* Signal `ALL_DEVICES` (F7.4), Ditto's opt-in cut after the fleet moves (F1.4), Zero's operator-moved window (F1.6, search summary).

**What every design shares.** Round one's option 2 still applies: a refusal that carries "Update now", background download and install on relaunch. Round one's option 4 (a minimum version with a deadline in `latest.json`) stays useful for retiring very old builds on the developer's schedule.

Confidence: high on what Git, Mercurial, SQLite, Signal-Server and Joplin's strings say (their source or specification), and on the rentable observations, including the drizzle SQL, which I ran. Medium on the per-release cost, which is an estimate from a grep, not a prototype. The Signal inactivity windows come from a search summary only.
