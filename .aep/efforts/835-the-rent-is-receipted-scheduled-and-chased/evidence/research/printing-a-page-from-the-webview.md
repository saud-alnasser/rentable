# Question

In this app as pinned (tauri 2.11.6, wry 0.55.1), can a page rendered in the webview, such as
a bilingual Arabic/English receipt or a multi-row payment schedule, be printed and saved as a
PDF on Windows (WebView2), macOS (WKWebView) and Linux (WebKitGTK)? Which of those paths are
reachable without forking Tauri or wry?

Five sub-questions from the brief:

1. Does `window.print()` open a print dialog on each platform, and is the old macOS problem
   (WKWebView ignores `window.print()`) fixed?
2. Does Tauri expose a Rust or JS `print()`? Which platforms implement it, and does it print
   the whole webview or one element?
3. Can a PDF be written with no dialog on each platform, and can Tauri or wry reach that today?
4. Can a JS PDF generator (pdf-lib, jsPDF, pdfmake) handle Arabic shaping and RTL?
5. Does `@media print` apply in each webview's print path?

# Findings

## 1. `window.print()` from the page

**F1.1: Windows. source.** wry's WebView2 backend makes its own `print()` evaluate
`window.print()` (`webview2/mod.rs:1712-1717`). Tauri leaves `window.print` untouched on
Windows; the comment in `plugin.rs:200` says "window.print works on Linux/Windows". A wry
maintainer confirmed in wry#1300 (2024-06-24): "On Windows, we simply call `window.print()` to
launch the panel, and it doesn't take any option." True of wry 0.55.1.

**F1.2: Windows, what the dialog is. source, weaker.** The reporter in wry#1300 (2024-06)
describes the dialog as the native WebView2 print preview. By default it adds a header (app
name or title) and a footer (the URL, `https://tauri.localhost/`), and the user can clear them
with a checkbox. Microsoft's print page says `ShowPrintUI` opens "the WebView2 Print Preview
dialog or the operating system's Print dialog". It does not say which dialog `window.print()`
opens. *Interpretation:* it is the browser (Edge-style) print preview, whose destinations
include saving as PDF. I did not verify this on a machine.

**F1.3: macOS, the historical problem. source.** WKWebView's public `WKUIDelegate.h` (WebKit
main) declares no print callback. The only delegate hooks that receive `window.print()` are
private: `_webView:printFrame:` and `_webView:printFrame:pdfFirstPageSize:completionHandler:`
(`WKUIDelegatePrivate.h:147-148`). A Tauri maintainer confirmed this in tauri#13451
(2026-03-12): the real fix "seems to require a private API", so it cannot ship to the App
Store. *Conclusion:* WKWebView still does not act on `window.print()` by itself, so this was
never "fixed" upstream in WebKit.

**F1.4: macOS, how Tauri works around it. source.** On macOS and iOS, Tauri's webview plugin
injects `scripts/print.js` as an init script (`plugin.rs:197-205`, comment: "need to use the API
on macOS"). The script replaces `window.print` with
`window.__TAURI_INTERNALS__.invoke('plugin:webview|print')`. That command calls wry's
`print()`. wry builds an `NSPrintOperation` from `-[WKWebView printOperationWithPrintInfo:]`
using the shared `NSPrintInfo`, margins defaulting to 0 (wry#1259), and runs it modally on the
window (`wkwebview/mod.rs:858-897`). The call only happens when the webview responds to that
selector (macOS 11+). Otherwise it silently does nothing (changelog: "Only run WebView::print on
macOS on v11+"). History: wry#235/#236 (2021-05) added it, and tauri PR #1738 routed
`window.print()` to it. True of tauri 2.11.6 / wry 0.55.1.

**F1.5: macOS, a permission gap in this repo. source + observation.** Because the replaced
`window.print` is an IPC call, it needs `core:webview:allow-print`. The `core:webview` default
set holds only `allow-get-all-webviews`, `allow-webview-position`, `allow-webview-size` and
`allow-internal-toggle-devtools` (`permissions/webview/autogenerated/reference.md`). This
repo's capability grants `core:default` and nothing more for webviews.
*Conclusion:* in this repo today, `window.print()` on macOS returns a rejected promise
(command not allowed) and shows no dialog, until `core:webview:allow-print` is added to
`capabilities/default.json`. Windows and Linux do not go through IPC and are not affected.
*Not run:* I read this from source and did not observe it on a Mac.

**F1.6: macOS, iframes. source.** In tauri#13451 / wry#1557 (Tauri 2.5.1, wry 0.51.2, macOS
15.4), `window.print()` works but `iframe.contentWindow.print()` does nothing. The maintainer
traced this to the same private-API limit. *Interpretation:* on macOS, printing from a hidden
iframe (the usual print-js / print-one-element trick) is not available.

**F1.7: macOS, dialog shape. source, dated.** wry#713 (macOS 12.6, 2022) reports that the dialog
differs from Safari's: larger margins, and no paper size or orientation controls. wry#1259
later set margins to 0 and added `print_with_options` (margins only). I did not re-verify on
current macOS whether paper size and orientation controls appear.

**F1.8: macOS 26 (Tahoe) risk. secondary.** An Apple DTS engineer (forum 811901, Jan 2026)
diagnosed an `EXC_BREAKPOINT` on Tahoe: the `WKPrintingView` returned by
`printOperationWithPrintInfo:` had a zero frame, and the fix is to set `op.view.frame =
webView.bounds` before running. wry 0.55.1 does not set the view frame (`wkwebview/mod.rs:881-895`).
A separate Apple bug, FB20581927 (forum 803249, Oct 2025 to Jan 2026), reports WKWebView print
page counts being miscalculated and output truncated, "classified as a serious bug", still
under investigation. *Interpretation:* wry's macOS print path may crash or truncate on macOS 26.
I found no wry or tauri issue that reports it. Unverified.

**F1.9: Linux. source.** Tauri leaves `window.print` alone on Linux (`plugin.rs:200`). WebKitGTK
emits `WebKitWebView::print` "when printing is requested on web_view, usually by a JavaScript
call, before the print dialog is shown", and the default handler shows the GTK print dialog
(WebKitGTK reference). wry's own `print()` on Linux does
`webkit2gtk::PrintOperation::new(&webview).run_dialog(None)` (`webkitgtk/mod.rs:679-683`).
Note that it passes no parent window. I did not check whether a dialog with no parent is modal
over the app.

## 2. A `print()` API on the Tauri side

**F2.1: source.** Tauri exposes `Webview::print()` and `WebviewWindow::print()` in Rust
(`webview/mod.rs:1485`, `webview_window.rs:2306`) and the IPC command `plugin:webview|print`
(permission `core:webview:allow-print`, off by default). The doc comment says: "Opens the
dialog to prints the contents of the webview. Currently only supported on macOS on `wry`.
`window.print()` works on all platforms." That comment is out of date against wry 0.55.1, which
implements `print()` on all three:

| Platform | wry 0.55.1 `print()` does |
| --- | --- |
| Windows | evaluates `window.print()` in the page |
| macOS | `NSPrintOperation` from `printOperationWithPrintInfo:`, run modally on the window |
| Linux | `webkit2gtk::PrintOperation::run_dialog` |

**F2.2: what gets printed. source.** Every path prints the webview's current top-level
document. There is no parameter for an element, a selection or a URL. WebView2's
`ShouldPrintSelectionOnly` exists only on the native `Print`/`PrintToPdf` settings, which Tauri
does not expose. *Interpretation:* to print "the receipt" rather than the app shell, either use
`@media print` rules to hide everything else in the current document, or open a separate
webview window at a receipt-only route and call print on that window.
`WebviewWindow::print()` targets a specific window. Iframes are ruled out on macOS (F1.6).

**F2.3: options. source.** The only print option wry exposes is margins, macOS only
(`WebViewExtMacOS::print_with_options`, `PrintOptions { margins }`). Tauri does not surface it.
wry PR #1317 ("Add API to allow print options", WebKitGTK plus macOS) is still **OPEN**. Tauri
issue #4917 ("Provide print API") is open with no maintainer plan (last activity 2025-12-31).
plugins-workspace #293 (print plugin) is open.

## 3. Writing a PDF without the print dialog

**F3.1: Windows. source.** WebView2 has `ICoreWebView2_7::PrintToPdf(path, settings, handler)`,
runtime 1.0.1020.30+. It "silently prints the current top-level document ... to a PDF file" and
overwrites an existing file. `ICoreWebView2_16::PrintToPdfStream` also exists. `PrintSettings`
covers orientation, page width and height (default 8.5x11 in), margins (default 1 cm), scale
(0.1-2.0), `ShouldPrintBackgrounds` (default FALSE), `ShouldPrintHeaderAndFooter` (default
FALSE) and `ShouldPrintSelectionOnly`. Only one print job may run at a time. All of these are
bound in the locked `webview2-com-sys 0.38.2`.
- *Reachable without a fork:* yes. `Webview::with_webview(|pv| pv.controller())` hands back the
  `ICoreWebView2Controller` on Windows (`webview/mod.rs:180`, `1668`). From it you get
  `CoreWebView2()` and cast to `ICoreWebView2_7`. That needs `webview2-com` (and `windows`) as a
  direct, `cfg(windows)` dependency at the same versions Tauri uses. Neither wry nor Tauri calls
  `PrintToPdf` today (grep of both at the locked versions). wry#707 asks for it and is open.

**F3.2: macOS. source.** Two native routes:
- `WKWebView.createPDF(configuration:completionHandler:)`, macOS 11.0+, returns PDF `Data`
  "from the web view's contents". It is bound in `objc2-web-kit 0.3.2` behind feature
  `WKPDFConfiguration`. *Secondary (forum 803249, Apple Frameworks Engineer, Oct 2025):* it
  draws "the exact same way it would draw to the screen or to print" and gives a vector PDF. The
  same thread reports that it **produces one very tall page**, and pagination settings do not
  apply. A wry#707 commenter (2026-05) makes the same claim. I did not confirm this against
  Apple's reference text, which does not discuss pagination.
- `WKWebView.printOperation(with:)`, macOS 11.0+, not deprecated in Apple's current docs. Pair it
  with an `NSPrintInfo` whose `jobDisposition` is `.save` ("Save to a file") and whose
  `jobSavingURL` is the target path, and set `showsPrintPanel = false`. *Interpretation:* this
  writes a paginated PDF without a dialog, through the same engine path as the print dialog.
  It carries the same Tahoe risks as F1.8, so set `op.view.frame` explicitly. Not run.
- *Reachable without a fork:* yes. `PlatformWebview::inner()` returns the `WKWebView` pointer and
  `ns_window()` returns the window (`webview/mod.rs:194-207`). Calling into them needs
  `objc2`, `objc2-app-kit` and `objc2-web-kit` as direct macOS dependencies. One real example
  outside this repo: Stirling-PDF linked PDFKit from Rust in a Tauri app to work around macOS
  printing (tauri#13451, 2026-03-13).

**F3.3: Linux. source.** `webkit_print_operation_print()` "Start[s] a print operation using
current print settings and page setup without showing the print dialog". With no settings, it
sends the job to the default printer. WebKit bug 212814 (REOPENED, unassigned) says
`GTK_PRINT_OPERATION_ACTION_EXPORT` is not implemented. Aiming at the "Print to File" printer
through `GtkPrintSettings` fails with "Printer not found", and printer names change with
locale. A 2024-07 comment notes that file printing exists internally (`findFilePrinter`) but has
no public API. A wry PR #1317 author (tauri#4917, 2024-07) gave up on silent PDF for WebKitGTK
for this reason.
- *Reachable without a fork:* the calls are reachable (`pv.inner()` returns `webkit2gtk::WebView`,
  and `set_print_settings` / `print` are bound in webkit2gtk 2.0.2). A reliable silent PDF on
  WebKitGTK is **not established**. The only documented path is the dialog's "Print to File"
  destination, which the user picks.

**F3.4: dialog-based PDF on every platform. interpretation, not verified here.** Each print
dialog offers PDF output chosen by the user: macOS's standard print panel has a PDF menu,
GTK's dialog has "Print to File", and WebView2's preview offers a PDF destination. None of
this needs code beyond F1/F2.

## 4. JS-side PDF generators and Arabic

**F4.1: pdf-lib. source.** In #657 ("RTL document"), the maintainer says: "Right now the only
way to do this is by drawing each character individually". Better text layout is "on the
roadmap". The repo's last push was 2024-07-17. Open #1450 reports Arabic with numbers coming
out reversed. There is no shaping and no bidi.

**F4.2: jsPDF. source.** `src/modules/arabic.js` shapes by substituting Unicode Arabic
Presentation Forms (isolated/final/initial/medial table), not OpenType GSUB. It only renders
correctly if the embedded font carries presentation-form glyphs. Open #3867 (2025-06) reports
most Arabic fonts failing, with missing and unconnected letters, and only Amiri "sort of"
working. Open #2747 reports Arabic alignment problems.

**F4.3: pdfmake. source.** #184 "Right to left language (RTL)" is still open.

*Conclusion:* none of the three shapes and orders Arabic mixed with English and digits to the
standard the webview's text engine already reaches. That is the same point wry#1300's reporter
made when choosing browser rendering over jsPDF.

## 5. `@media print`

**F5.1: WebKit (macOS and Linux). source.** When WebCore prints a frame, `PrintContext::begin`
calls `frame->setPrinting(true, …)` (`PrintContext.cpp:231`). `LocalFrameView::
adjustMediaTypeForPrinting(true)` switches the frame's media type to `print` and restores it
afterwards. *Interpretation:* `@media print` applies to `printOperationWithPrintInfo:`, to GTK
print operations and to both dialogs. `createPDF` is described as drawing "the exact same way it
would draw to the screen or to print" (secondary). Whether it uses screen or print media was
**not established**.

**F5.2: WebView2. not sourced by me.** Microsoft's print page does not mention media types. I
believe Chromium's print path uses print media for `window.print()`, `ShowPrintUI` and
`PrintToPdf`, but I did not trace that in Chromium source. It stays open. `@page` margins versus
`PrintSettings` margins: not checked.

**F5.3: source, dated.** wry#713 (2022) says "The @page rule is not implemented with Safari".
That is stale for current WebKit and I did not re-verify it.

# Conclusion

Per platform, at tauri 2.11.6 / wry 0.55.1:

- **Windows (WebView2).** `window.print()` opens WebView2's print preview. By default it may
  print a header and footer with `https://tauri.localhost/`, which the user can clear. A silent
  paginated PDF is available natively (`PrintToPdf`, full page, margin and header/footer
  control) and can be reached through `with_webview` + `webview2-com` without a fork.
- **macOS (WKWebView).** WKWebView still ignores `window.print()` natively. Tauri swaps it for
  an IPC call into wry's `NSPrintOperation`, and in this repo that call **is blocked until
  `core:webview:allow-print` is granted**. Iframe printing does not work. A silent PDF is
  reachable through `with_webview` + objc2. Use `printOperation(with:)` with a save disposition
  to get pages; `createPDF` reportedly gives one tall page. On macOS 26 there are Apple-side
  print bugs (zero-frame crash, truncation) that wry does not guard against. Unverified.
- **Linux (WebKitGTK).** `window.print()` opens the GTK print dialog, and "Print to File" there
  produces a PDF. A **silent** PDF is not reliably available: WebKit bug 212814 is open.
- **Everywhere.** Tauri's print prints the whole top-level document with no element target and
  only macOS margins as an option. The official print-options work (wry PR #1317, tauri#4917) is
  unmerged. To print one receipt or schedule, either hide the rest with `@media print` or print
  a dedicated window. `@media print` is confirmed from source for WebKit's print path and is
  assumed but unsourced for WebView2. JS PDF libraries are not a viable route for shaped,
  bidirectional Arabic.

This file records findings only. It does not choose an approach.
