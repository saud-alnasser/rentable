# Does the Google Drive API v3 support a conditional update — a compare-and-set — on an existing file's content or metadata?

Verified against: Google Drive API v3, 2026-08-02
Status: answered, with one open question — whether Drive v3 emits an `ETag` HTTP *response* header was not verified against a live authenticated response (see Limitations). It does not change the answer, because there is no request-side precondition to pair such a header with.

## Answer

No. Drive API v3 offers no compare-and-set on `files.update`, for content or for metadata. The `File` resource has no `etag` field — the string `etag` does not occur anywhere in the v3 Discovery document (v2's `File` still carries one, so this is a v3 removal, not an oversight). `files.update` accepts no precondition query parameter of any name, and no method in the entire API accepts one. The generated first-party Go client contains zero occurrences of `IfMatch` across 487 KB; the `IfNoneMatch` it does expose is on read calls only — a cache-validation primitive, not a guard on a write. `File.version` is **Output only**, so it cannot be sent back as a precondition even though the current code reads it; `headRevisionId` is likewise Output only, and the `revisions` collection permits no content write and no conditional write at all.

That means the check-then-write window in the manifest rewrite is **not closable at the API**. Drive's only documented mechanism in this area is detection after the fact: the `changes` collection, whose own documentation states an application must persist prior state and compare it itself. Google never documents lost-update guidance explicitly — that absence is reported here as an absence, not as a recommendation. The design choice is therefore between porting the existing check-then-write as-is (accepting a window that cannot be closed), and moving atomicity somewhere Drive does guarantee it — a distinct-name write plus a rename, or an application-level lease — none of which the API endorses in writing.

## Findings

- The v3 `File` resource has no `etag` field; the substring `etag` occurs **0 times** in the whole v3 Discovery document (revision 20260728) — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), `schemas.File.properties`, whole-document scan
- The v2 `File` resource *does* carry `etag`, described as "Output only. ETag of the file." — so v3 dropped it — [Drive v2 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v2/rest), `schemas.File.properties.etag` (revision 20260728, same day as the v3 doc fetched above)
- `files.update` accepts exactly these query parameters, none of them a precondition: `addParents`, `enforceSingleParent`, `fileId`, `includeLabels`, `includePermissionsForView`, `keepRevisionForever`, `ocrLanguage`, `removeParents`, `supportsAllDrives`, `supportsTeamDrives`, `useContentAsIndexableText` — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), `resources.files.methods.update.parameters`; corroborated by [Method: files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update), "Query parameters"
- No `precondition`, `ifMetadataMatches`, `ifGenerationMatch`, `ifMatch`, or `generationMatch` parameter exists on **any** method in the API — each of these substrings occurs 0 times document-wide — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), whole-document scan over the union of every method's parameter names
- `File.version` is **Output only**: "Output only. A monotonically increasing version number for the file. This reflects every change made to the file on the server, even those not visible to the user." — it cannot be supplied as a precondition — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), `schemas.File.properties.version`; same description (minus the "Output only." prefix in the rendered page) at [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), "version"
- `headRevisionId` is Output only and content-only: "Output only. The ID of the file's head revision. This is currently only available for files with binary content in Google Drive." — no parameter accepts it on update, so it cannot pin a write — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), `schemas.File.properties.headRevisionId`
- The `revisions` collection permits no conditional write: `revisions.update` is `PATCH files/{fileId}/revisions/{revisionId}` taking only `fileId` and `revisionId`, and the writable `Revision` fields are limited to `keepForever`, `published`, `publishAuto`, `publishedOutsideDomain`, and `modifiedTime` — no content, no precondition — [Drive v3 Discovery document](https://www.googleapis.com/discovery/v1/apis/drive/v3/rest), `resources.revisions.methods` and `schemas.Revision.properties`
- The first-party generated Go client contains **0 occurrences** of `IfMatch` and of the literal `If-Match` across the full 487 KB of generated code — [drive/v3/drive-gen.go](https://raw.githubusercontent.com/googleapis/google-api-go-client/main/drive/v3/drive-gen.go), whole-file scan
- The same client exposes `IfNoneMatch` on 28 call types, **all** of them reads (`FilesGetCall`, `FilesListCall`, `ChangesListCall`, `RevisionsGetCall`, …); `FilesUpdateCall` and `RevisionsUpdateCall` do not have it. Its own doc comment describes cache validation, not compare-and-set: "IfNoneMatch sets an optional parameter which makes the operation fail if the object's ETag matches the given value. This is useful for getting updates only after the object has changed since the last request." — [drive/v3/drive-gen.go](https://raw.githubusercontent.com/googleapis/google-api-go-client/main/drive/v3/drive-gen.go), generated `*Call` methods
- Drive's error guide documents 200, 400, 401, 403, 404, 429, 500, 502, 503, 504 — **no 412 Precondition Failed and no 409 Conflict**, the statuses a precondition primitive would necessarily produce — [Resolve errors](https://developers.google.com/workspace/drive/api/guides/handle-errors), status code listing
- The single mention of ETags anywhere in Drive's v3 guides is generic, conditional boilerplate that does not assert Drive uses them: "If ETags are used by the API, the server updates ETag values when it successfully processes a patch request, just as it does with `PUT`." — [Improve performance](https://developers.google.com/workspace/drive/api/guides/performance), patch semantics section
- Google's documented mechanism for noticing another client's write is detection, explicitly pushed to the client: "A change does not provide a delta between revisions. Applications that need to know which properties have changed should persist the previously known state of the item and compare." — [Track changes for users and shared drives](https://developers.google.com/workspace/drive/api/guides/about-changes), "Enable change entries"
- Change tracking is a poll over a token cursor — `changes.getStartPageToken` then `changes.list`, chronological, `newStartPageToken` on the last page — i.e. after-the-fact detection with no ordering guarantee relative to a write in flight — [Retrieve changes](https://developers.google.com/workspace/drive/api/guides/manage-changes), token workflow
- Neither the upload guide nor the API overview nor the revisions guide discusses concurrent writes, conflicts, or lost updates; the upload guide's only statement on rewriting is "To update an existing file, use `PATCH`." — [Upload file data](https://developers.google.com/workspace/drive/api/guides/manage-uploads); [Drive API overview](https://developers.google.com/workspace/drive/api/guides/about-sdk); [Manage file revisions](https://developers.google.com/workspace/drive/api/guides/manage-revisions)
- Relevance to the current code: `did_remote_head_change_from_manifest` compares `file.version` against `head.revision` at `tauri/src/remote_sync/google/conflict.rs:329` and `modifiedTime` at :333 — both are valid *change detectors* per the field descriptions above, and neither can become a precondition

## Limitations

- **Not verified against a live authenticated response.** No Drive credentials were available, so whether Drive v3 returns an `ETag` HTTP *response* header was not observed directly; an unauthenticated probe of `GET /drive/v3/files/{id}` returned 403 with no `ETag` header, which proves nothing about authenticated responses. A Discovery document describes fields and query parameters, **not** HTTP headers, so it cannot by itself rule out an undocumented `If-Match` request header. The finding that no such header is supported rests on the converging absence of `IfMatch` from the generated first-party client, the absence of 412 from the documented error set, and the removal of `etag` from the resource — not on the Discovery document alone. Resolving this definitively would take one authenticated `files.update` carrying `If-Match: *` and observing whether it 412s or is ignored.
- **"No documented guidance" is an absence, not a statement.** Google nowhere says "Drive offers no optimistic-concurrency primitive", and nowhere gives lost-update guidance for two clients rewriting one file. Per the rule against treating silence as proof, the correct characterisation of Google's *guidance* is **not documented either way**. The non-existence of the precondition *primitives* is a positive finding, since the Discovery document is a complete enumeration of fields and parameters.
- **Whether `File.version` increments on a metadata-only edit is inferred, not read.** The description says it "reflects every change made to the file on the server, even those not visible to the user", which implies metadata-only edits bump it, but Google does not enumerate the triggering operations. Treat "a permission or `appProperties` change bumps `version`" as inference. The practical consequence for the current code: `version` is a *coarse* change detector that can fire on changes unrelated to manifest content.
- **`IfNoneMatch` in the Go client is generic `googleapi` machinery** emitted for read methods across all Google APIs; its presence does not prove Drive honours `If-None-Match`. It was used here only as evidence about `If-Match`'s absence, which is a whole-file zero and does not depend on that caveat.
- No secondary source is load-bearing for any claim above. Web-search summaries encountered during this pass asserted that Drive v3 supports `If-Match` conditional updates; that assertion was checked against the Discovery document and the generated client and is **false**, and it is recorded here only as a warning that it circulates.
- Not checked: the Drive v3 batch endpoint's header handling, the `drive.appdata` scope's folder semantics, and whether Google Docs-native files behave differently from binary files with respect to `version` (the manifest is binary JSON, so this did not bear on the question).
