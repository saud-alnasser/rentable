# changesets

How a user-visible change gets into the changelog and into a release.
[[rules/version-control]] says *when* one is required; this says how to write it.

The repository is a pnpm workspace and **`@rentable/desktop` — the desktop application at
`apps/desktop/` — is the package a changeset is written against.** The root is named `rentable`,
private, unversioned, and not something changesets versions.

**`@rentable/control-plane` is the second package and has never had a changeset written for it**
*(added 2026-08-18 by #549)*. Nothing about it reaches a user: it ships in no artifact, the
updater never sees it, and it is deployed nowhere — so by *When one is not needed* below, its
changes do not get one. If it is ever released, `privatePackages` versions and tags it under its
own name, and `release.yml`'s tag glob is already written to keep the two apart.

Both packages are **private**, so nothing is published to npm. `privatePackages` in
`.changeset/config.json` sets `version: true` and `tag: true` — changesets bumps the version
and the release workflow tags it, and the tag is what triggers the signed Tauri artifact
build. The changelog is generated by `@changesets/changelog-github`, which turns each entry
into a line crediting the pull request.

Docs: <https://github.com/changesets/changesets/blob/main/docs/intro-to-using-changesets.md>.
Fetch before changing `.changeset/config.json` or reaching for a command below not listed.

## Add a changeset

**Write the file directly.** Do not run `pnpm exec changeset` in a non-interactive
session — it is a prompt-driven wizard (which package, which bump, then a summary) and it
hangs with no terminal attached.

A changeset is a markdown file in `.changeset/` with any unused name. The generated names
are three random words; anything unique works, and the file is deleted on release:

```markdown
---
'@rentable/desktop': patch
---

summary in the imperative, lowercase, one line
```

`'@rentable/desktop'` is the package to name — **quote the scoped name exactly**, including the
leading `@`. The bump is `patch`, `minor`, or `major`, and it drives the version directly —
there is no separate release-notes step where it can be corrected later.

`apps/desktop/CHANGELOG.md` keeps its `# rentable` heading rather than being retitled to the
package name. The heading is the product's and the file is 488 lines of its history; changesets
prepends under whatever heading it finds, so leaving it is what keeps that history continuous.

The summary lands in `CHANGELOG.md` verbatim, so write it for someone reading release notes,
not for a reviewer reading the diff.

## Where it lives

**In the same branch and the same commit as the change it describes** — never on a branch of its
own. A changeset is that change's changelog entry, so the entry and the diff it announces are one
reviewable thing, which is what [[rules/version-control]]'s *one ticket, one branch, one commit*
already makes the default.

Separated, they can land apart: the entry merges, the change it announces does not, and the
changelog describes a release that does not contain it.

The shape this rules out is a `chore:` branch carrying nothing but a changeset — **including when
the reason for it is that a release needs a version bump and nothing user-visible is in flight.**
That reason feels like an exception and is not one. Either something is shipping, in which case
the changeset belongs on its branch and describes *it*, or nothing is, in which case no changeset
is due and the version is right where it is.

## When one is not needed

Dependency bumps and internal refactors that no user can observe do not get a changeset.
**Nor does anything in `apps/control-plane/`, for the same reason and not as an exception to
it**: a user cannot observe a package that ships in no artifact.
A missing changeset on a user-visible change means it ships without appearing in the
changelog — the failure is silent, since nothing in CI checks for one.

## Never run the release path locally

```bash
node .github/changeset-version.cjs   # do not run
node .github/changeset-tag.cjs       # do not run
```

Both belong to `.github/workflows/release.yml` and both are destructive outside it.
`changeset-version.cjs` runs `changeset version`, then rewrites
`apps/desktop/tauri/Cargo.toml`'s version to match `apps/desktop/package.json` and refreshes both
lockfiles. `changeset-tag.cjs` **creates a git tag and pushes it** — publishing, and the human's
call under the standing rule in [[policies/engineering]].

**Both read the desktop package, never the root.** The workspace root is private and carries no
`version` at all, so a script pointed at it would tag `undefined` — and the failure would be
discovered by users on the release after it, not by CI.

## The tag, and what the updater actually reads

The release tag is **`@rentable/desktop@<version>`** — changesets' own convention for a package
in a workspace. It replaced `v<version>` on 2026-08-17.

**No installed application noticed, because none of them reads the tag.** The updater polls a
fixed endpoint, `releases/latest/download/latest.json`, which GitHub resolves through its
latest-release pointer — most recent non-draft, non-prerelease release by date, tag name never
consulted. `tauri-action` writes that manifest's `version` field from the *app's* version, not
from `tagName`. The plugin then compares `release.version > self.current_version` as semver.

So the contract is the endpoint, that `version` field, and the signing key. The tag is internal,
and the pre-workspace `v*.*.*` tags are kept rather than deleted because the five published
releases still point at them. Sources are in
[[efforts/the-repository-becomes-a-monorepo/evidence/research/the-updater-contract]].

**What would break it** is not a tag rename but any of: changing the endpoint, leaving the
release a draft, marking it a prerelease, rotating the signing key, or a `version` field that
does not sort above what is installed.

On `main`, `changesets/action` opens a `chore: version package` pull request that consumes
the accumulated changeset files. Merging that pull request is what releases.
